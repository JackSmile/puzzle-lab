## Замечания

### [P2] Линейные предупреждения короче реальной области попадания

`games/duskbound/bestiary-render.mjs:49–51`, дополнительно `:82`.

`shape()` рисует прямоугольник с плоскими торцами. Модель использует расстояние до **отрезка**, то есть область с круглыми торцами: `geometryHit()` для Chain Pull проверяет `segmentDistance <= width/2 + target.radius`; Rhoa проверяет `segmentDistance <= enemy.radius + target.radius`. Поэтому герой, чья окружность целиком за пределами предупреждения, получает попадание. Это сохраняется и в reduced effects: используется тот же путь.

Подтверждено двумя независимыми сценами через публичные функции модели (не через `core.tick`, интеграция которого ещё ожидается):

- Rhoa `(0,0)`, исходная цель `(180,0)`, немедленное начало windup. Полученный action: `x=0, x2=360, width=38`. После фиксации направления герой перемещён в `(380,0)`, radius 12. Его ближайшая точка `x=368` находится на 8 мировых единиц дальше плоского торца предупреждения. За 60 шагов по 0.025 с damage callback вызван **один раз**. Дополнительно, половина ширины предупреждения 19 не равна реальному радиусу Rhoa 20, используемому при swept collision.
- Brutus `(0,0)`, цель `(180,0)`, `telegraph=0, shotTimer=0`. Полученный Chain Pull: `x=0, x2=430, width=32`. После фиксации направления герой перемещён в `(450,0)`, radius 12: ближайшая точка `x=438` за пределами предупреждения. За 45 шагов по 0.025 с callback вызван **один раз**: расстояние до конечной точки 20 попадает в фактические `16+12=28`.

Исправление: рисовать capsule с торцами того же радиуса, который использует модель. Для Rhoa брать действительный `enemy.radius`, а не полагаться на фиксированную action.width. Проверить точку за концом траектории и боковой край; радиус героя уже учитывается моделью отдельно и не должен дважды добавляться в изображение. В текущей штатной генерации элитными становятся Drowned, поэтому отдельную встречу с elite Rhoa не заявляю как воспроизведённую; вывод о нормальной Rhoa и Chain Pull от этого не зависит.

### [P2] Выбор записи уничтожает элемент с клавиатурным фокусом

`games/duskbound/bestiary.mjs:44–49`, вызов `:52`.

Обработчик каждой кнопки picker вызывает `updateSelection()`, который синхронно вызывает `updatePicker()` и `replaceChildren()` для всех кнопок. Исходная активная кнопка удаляется; новый элемент с тем же `data-entry` не получает фокус. После выбора записи клавиатурой выбранная кнопка уже не является активным элементом, и её индикатор клавиатурного фокуса пропадает. Для каталога из 17 предметов это теряет контекст текущего выбора. Точная стартовая точка последующего Tab зависит от поведения браузера и здесь не проверялась.

Исправление: обновлять `aria-pressed` существующих кнопок или восстанавливать фокус на новой выбранной кнопке, только если фокус до обновления находился в picker. При смене вкладки не перетаскивать фокус с кнопки вкладки без необходимости. Это вывод по прямому пути удаления DOM-узла; браузерное воспроизведение намеренно оставлено владельцу интеграционной UI-проверки. Проверка после исправления: Tab к Merveil → Enter → фокус остаётся на Merveil → Tab переходит к Dominus; аналогично для соседних unique.

- Отсутствие подключения `tickEncounters` в текущем core не оформлено дефектом Task 4: это заявленный будущий Task 3. По той же причине не заявляю работоспособность playback, переключения сердца или item hooks в браузере.
- Три существующих equipment projection tests были переданы как прошедшие; в этом ревью они не перезапускались. Путь сравнения использует независимые structured clones, а карточки replacement перечисляют `replacement.items`.
- Основной run, загрузка ресурсов по HTTP, консоль, mobile/desktop компоновка, фактический фокус и reduced-effects снимки остаются на интеграционной браузерной проверке родителя. Просмотр PNG сам по себе не подтверждает геометрию anchor или читаемость готового интерфейса.
